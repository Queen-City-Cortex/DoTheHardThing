# Hosting

What the hosting config promises, and the check that holds it:

- **Theme color.** The light `<meta name="theme-color">` in `index.html` (`#f4f3ef`, the paper) owns the color of the installed app's title bar and splash. `vite.config.ts` repeats it as a literal in the manifest's `theme_color` and `background_color` (the config has no Node types to read `index.html` with), and `npm run check:dist` fails when either, or the light `--paper` in the built CSS, differs from the meta tag. The dark meta tag (`#15181d`) has no manifest counterpart: a manifest holds one color. The icons keep their charcoal (`#1f2329`, the ink color) background.
- **Orientation.** The manifest has no `orientation`, so the installed app follows the device's rotation (the platform default). It was locked to portrait; a landscape probe of every screen at 844x390, 667x375 and 932x430 found nothing unreachable, clipped or overflowing, only cramped spots: the block's timer card keeps its 240 px minimum, so its buttons and the first visit's Start sit below the fold, and the sticky action row covers about a fifth of the height. `npm run check:dist` fails on any lock value (`portrait`, `landscape` and their `-primary` and `-secondary` variants); `any` and `natural` pass. The live manifest is compared byte for byte with the build by `verify:live` (Live checks of this build, below), so a deployed lock shows there too.
- **Security headers.** One `/*` rule in `public/_headers` gives every static response `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()` (features the app never uses; notifications and the service worker are not governed by it) and `X-Frame-Options: DENY` (no other site can frame the pages). The values live once, in `POLICY` in `scripts/headers-policy.mjs`, which also holds the `_headers` parser that `check:dist` and `verify:live` share. `npm run check:dist` fails when `/`, `/sw.js`, `/manifest.webmanifest`, a hashed `/assets/*.js` or an unknown path such as `/nope` (the single-page-app fallback; Cloudflare matches `_headers` on the request path; that the fallback gets them is measured with local `wrangler dev` only and `verify:live` compares `/` only, so after the first deploy run `curl -sI https://dothehardthing.app/nope` once) lacks one of them or gets another value. None of the four can block the optional Cloudflare Web Analytics beacon (the `static.cloudflareinsights.com` script and its request to `cloudflareinsights.com`): none restricts scripts or connections.
- **Content-Security-Policy, Report-Only.** The `/*` rule also sends `Content-Security-Policy-Report-Only: default-src 'self'; script-src 'self' https://static.cloudflareinsights.com; connect-src 'self' https://cloudflareinsights.com; img-src 'self'; style-src 'self'; font-src 'self'; manifest-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. Report-Only blocks nothing: a violation is only a console message. It has no `report-uri` or `report-to`, since the repo has no endpoint. It was derived from the built page: `index.html` loads only same-origin scripts, the stylesheet, the SVG favicon, the PNG icons and the manifest, with no inline script or style; the CSS loads only same-origin `url(/assets/*.woff2)`; the JS fetches only `/api/event` (and the modulepreload polyfill's same-origin fetch); React's `style` props go through CSSOM, which CSP does not govern; no `data:` or `blob:` image; the service worker and its `importScripts` of workbox are same-origin. The two outside origins are the Web Analytics beacon: `beacon.min.js` from `static.cloudflareinsights.com` (`script-src`), which posts to `https://cloudflareinsights.com/cdn-cgi/rum`, or to the same-origin `/cdn-cgi/rum` when the edge injects it (`connect-src`). The value lives in `CSP_DIRECTIVES` in `scripts/headers-policy.mjs`; any origin other than `'self'` and `'none'` must be listed in `CSP_ORIGINS` there, with the directive that must keep it. `npm run check:dist` fails when a path class lacks the exact value, when it has a report endpoint, drops a beacon origin or names an origin off that list, and on an enforcing `Content-Security-Policy` header. `verify:live` compares it on `/` with the other headers of this build. `e2e/csp-watch.mjs` logs every violation in every journey page (e2e/README.md, CSP watch); all non-gap journeys under `wrangler dev` with this policy logged none.
- **Enforcing the CSP is a later owner decision, not part of this change.** The steps, after a clean soak of the Report-Only header on the live site: open the live app in a browser with the console open on each screen and see no `[Report Only]` CSP message; rename the header to `Content-Security-Policy` in `public/_headers` and change `check:dist` (which refuses it until then) and `LEFT_OUT`; deploy; check `curl -sI https://dothehardthing.app/` shows `content-security-policy` with the same value; and check the Cloudflare Web Analytics dashboard still receives page views the day after. The risk: local tests cannot prove what the production edge delivers. `wrangler dev` simulates asset serving; a beacon test with a fake token on `127.0.0.1` showed the script loads and runs and its POST to `cloudflareinsights.com/cdn-cgi/rum` is attempted with no violation (it then fails on CORS for the local origin, with or without the policy), but the beacon Cloudflare injects at the edge on the live site, its configuration and where it posts there, are seen only in production. An enforcing CSP that is wrong drops the analytics silently, or breaks the page.
- **Not the Worker.** Cloudflare applies `_headers` only to static asset responses, not to responses the Worker makes, so `/api/event` gets none of these headers (it returns no page).
- **Left out on purpose.** No `Strict-Transport-Security`: the `.app` TLD is on the browsers' HSTS preload list, so browsers already refuse plain HTTP for the domain; which subdomains exist beyond `www` is not known to the repo, and `includeSubDomains` is hard to undo once browsers have cached it. No enforcing `Content-Security-Policy` yet (it is sent Report-Only, above). `verify:live` reports both as INFO (`LEFT_OUT` in `scripts/headers-policy.mjs`).
- **www.** `www.dothehardthing.app` is a custom domain of the Worker in `wrangler.jsonc` (its DNS record and certificate); a Cloudflare redirect rule, created by hand in the dashboard and not by the repo or CI, should send it to the bare domain with a 301. The runbook is [www-redirect.md](../www-redirect.md); `npm run verify:live -- --www` reports it (PENDING until the rule exists, `--require-www` to fail instead). CI cannot prove it.
- **robots.txt.** `public/robots.txt` (`User-agent: *`, `Allow: /`, no `Sitemap` line since there is no sitemap) is a real static file, so Cloudflare serves it as `text/plain` before the single-page-app fallback, which used to answer `/robots.txt` with the app HTML. It is not in the service worker precache and `navigateFallbackDenylist` is unchanged, so a person who types `/robots.txt` into an installed app gets the app shell from the service worker; crawlers run no service worker. `npm run check:dist` fails when `dist/robots.txt` is missing, has no `User-agent:` line, holds HTML or a line that is not `Field: value`, or `_headers` gives it another Content-Type. If the zone's managed robots.txt option (the AI bots setting in the Cloudflare dashboard) is ever turned on, Cloudflare prepends its own lines, the live bytes stop equalling this file, and `verify:live --post-deploy` fails on it: turn the option off or change the check on purpose.
- **Unknown paths stay 200.** Every other unknown path still gets the app shell (200). A 404 (`assets.not_found_handling: "404-page"` or a Worker change) would change what every unknown URL does, and the service worker's navigation fallback would still show the app shell to returning visitors, so the server and the service worker would disagree; left as it is on purpose.
- **Live checks of this build.** `npm run verify:live` compares the live `manifest.webmanifest` and `robots.txt` (200 `text/plain`, the same bytes) with `dist/`'s, and the headers live `/` gets with what `dist/_headers` gives `/` (`content-type` aside, per header name, whitespace collapsed; headers the edge adds are ignored). These checks of this build's files are a FAIL only with `--post-deploy` ("I just deployed this build"), which the deploy job passes and `check:workflows` requires; without it a mismatch prints `PENDING ...; run with --post-deploy after the deploy`, which never fails the run on its own, so the checks can run against the live site before a deploy. The entry script cannot decide it: a change to `_headers`, the manifest or `robots.txt` alone changes no JS, so the entry script is the same before and after the deploy. `scripts/verify-live.test.mjs` runs it against a local fake site.
