# Architecture

Do The Hard Thing is a static single-page app plus one tiny Cloudflare Worker.

## Pieces

| Path | What it is |
| --- | --- |
| `src/` | The app: Vite, React 18 and TypeScript. `App.tsx` holds the screens and their side effects; `state.ts` is the screen state as one value and the pure reducer that changes it; `logic.ts` is the pure day logic (items, tags, blocks, counts); `method.ts` holds the method's rules and numbers as data; `copy.ts` holds every word the app shows; `storage.ts` reads and writes `localStorage`; `reminder.ts` schedules the optional morning notification; `analytics.ts` is the anonymous-count client; `clock.ts` reads the device clock; `events.ts` is the event list shared with the Worker; `decode.ts` turns stored JSON into typed days. Tests sit beside the code as `*.test.ts` (Vitest). |
| `worker/index.ts` | A Cloudflare Worker. Requests to `/api/*` run it first. It handles `POST /api/event`, answers 404 or 405 for anything else under `/api/`, and everything else is served from `dist/` by the assets binding. |
| `wrangler.jsonc` | Worker config: static assets from `./dist`, single-page-app fallback, `run_worker_first` only for `/api/*`, the Analytics Engine binding, and the production routes. |
| `vite.config.ts` | Vite config and `vite-plugin-pwa` (service worker, web manifest). Also adds the optional Cloudflare Web Analytics beacon at build time. |
| `e2e/` | Playwright journeys that drive a production build in headless Chromium. See [`e2e/README.md`](../e2e/README.md). |
| `scripts/screens.mjs` | Regenerates `docs/screenshots/`. |
| `scripts/og/card.mjs` | Rebuilds the link preview card `public/og-image.png` from a live screenshot of the Pick screen (see the README). |

## Module map

Each platform API has one owner module in `src/`. Every other module calls the owner, so a second copy of a date key, a storage read or a permission check cannot appear.

| Owner | Owns | Others use |
| --- | --- | --- |
| `storage.ts` | `localStorage`, parsing stored JSON (through `decode.ts`) | `load`, `save`, `refresh`, `kv()` and `readSmall()` for a small key |
| `clock.ts` | `Date.now()` and `new Date()` with no argument | `now()`, `today()`, `isLate(t, cutoff)`; pass the number down |
| `reminder.ts` | `Notification`, `navigator.serviceWorker` | `askPermission`, `askPermissionIfUnasked`, `readPermission`, `notify`, `scheduleReminder` |

`logic.ts`, `state.ts`, `method.ts`, `events.ts` and `copy.ts` are pure: they take every value as an argument (the time too), `logic.ts` imports only `method.ts` and `copy.ts`, `state.ts` only `logic.ts`, and the other three import nothing (`clock.ts` imports `logic.ts` and `method.ts`, never the other way; `reminder.ts` imports `copy.ts` for the notification's words). Each owner module imports only what its entry in `OWNER_IMPORTS` lists, `.ts` modules never import React, and the Worker imports only `events.ts` from the app. The `OWNERS` table in `eslint.config.js` turns this map into lint errors that name the function to call, and `scripts/boundaries.test.mjs` checks what those rules catch. Tests are exempt, since they stub the globals.

## The screen state

`src/state.ts` holds what the app is showing as one value, `State`, and changes it only through `reduce(state, action, now)`. It is pure: it imports only `logic.ts` and takes the time as `now`. `App.tsx` keeps it with `useReducer`, and its `send(action)` reads `now()` from `clock.ts` once per action and hands it in. (The Pick screen's late line is the one clock read at render time.)

`State` is a discriminated union on `screen`. Each variant carries exactly what its screen needs, so a state the UI cannot show cannot be written down (`tsc -b` rejects it; `src/state.property.test.ts` has an `@ts-expect-error` line for each rule):

- the seven day screens (`Base`): `welcome`, `name`, `ask` and `pick` plan a day with no block yet (`PlanDay`) and carry `small`, the bad-day shorter-block toggle, which exists only while planning; `pick` also carries `list` (`pickOrder` of the items) and `chosen` (one of them, or null, always agreeing with `day.chosenId`), built only by `pick()`; `block` carries a running block (`RunningDay`) and the `now` its countdown is drawn from; `close` an ended block (`EndedDay`); `closed` a closed day;
- the overlays `about` and `days` carry `under`, the day screen they go back to, and `prev`, the overlays opened before them, so Done goes back one step and there is no separate stack to clear.

There are 21 actions, one per button plus `tick` (the block countdown), `rollover` (the date check, with the stored days) and `otherTabClosed` (what another tab saved for this date). Both switches, on the screen in `reduceBase` and on the action in `reduce`, end in `never()`, so a new screen is a compile error until `reduceBase` has a case for it, and a new action until `reduce` lists it. Which screen handles an action is a `reduceBase` case added by hand: an action that every screen ignores compiles, and only the property test notices (its weighted comparison fails when an action never changes the state). The render in `App.tsx` is a `switch (s.screen)` that ends the same way.

What the reducer owns: which screen shows, the day's record while it is open, the toggle, the way back from the overlays, and settling the block (a block action or a tick that ends the block moves to Close in the same step; the old App.tsx did this in an effect, and in another effect left the block screen once a block had ended). What stays in `App.tsx`: saving (`putDay` into the store and `save()`, the save note), pulling in other tabs' saves, the anonymous counts, asking for notification permission on Start, "Your block is done" (sent when `completed(prev, next)` says a step settled a block to complete, never on End block), the morning reminder, focus after a screen change, the one-second block timer, and the date checks.

Ordering notes:

- **Rollover.** `App.tsx` checks the date in a layout effect (on a change of the day, the day screen, the store or the screen, every minute, and on focus and visibility). When `shouldRollOver` says yes it saves the day being left first, `save(putDay(store, day), day.date)`, while it is still the open day (after the move a merge would prefer the older stored copy), then sends `rollover`, which re-checks the same question and opens today's stored record or a new day.
- **Closing a day carried past midnight** is two transitions: `closeDay` (to Closed), then the layout effect's `rollover`, before the browser paints, so Closed is never shown and the carried day is saved closed exactly as before.
- **The first tick.** A block that ended while the app was closed opens on the block screen and settles on the `tick` `App.tsx` sends once when it opens (the old App.tsx's settle effect ran once on the first render), so Close and "Your block is done" follow as before.

`src/state.property.test.ts` runs 5000 seeded sequences of up to 40 actions (uneven time steps up to 20 hours, an occasional reload from the stored days) three ways: a model of the App.tsx this replaced (8f5dbaa; its handlers and its effects, with switches to leave out each repair) against the invariants; the reducer against the same invariants, with any action at any time and UI-gated; and the reducer, inside a model of the new App.tsx, against the old model step by step (same screen, same way back, same day record, same stored days, same notifications, and the same toggle while planning). The UI-gated sequences come in two mixes of 5000 each. The uniform one is the original: it spends most steps on Welcome, Name and the overlays, and the pinned seeds depend on it. The weighted one (own buttons weigh 3 against 1 for an overlay or Back, another tab closes the day 0.5% of the time, edits mostly add) reaches Pick, the block, Close, Closed and midnight, and its comparison asserts a floor for how often each action changed the state and each screen was on show. After midnight another tab has sometimes saved a record for the new date before the check, so the rollover must open it. With screenForBlock left out on its own the first invalid state is at seed 82, step 21, and with validChoice left out at seed 38359, step 31; both are asserted. Leaving out the stack clearing breaks no invariant: only the comparison (its `back`) sees it. `REPLAY=1` runs the invariants as a must-pass check on the old logic without its repairs and fails on the 6ef125f state, the block screen with a stopped block (seed 82, step 21).

### Adding a screen

1. Add a variant to `Base` in `src/state.ts` carrying exactly its data, and its name to `DayScreen` in `src/logic.ts` (a compile-time check in `state.ts` fails until the two agree, and so do the `shouldRollOver` call sites in `App.tsx`, `state.ts` and the property test's model). `tsc -b` then fails until `reduceBase` has a case for it.
2. Add its actions to `Action`. `tsc -b` fails until `reduce` lists them; the case that handles each one in `reduceBase` is yours to add, since an action no screen handles compiles.
3. Update `resume` if the screen should survive a reload.
4. Add its render branch to the `switch` in `App.tsx`; `tsc -b` fails at `S.never` until you do.
5. Add it and its actions to the generators (`gated`, `anyAction`) and the invariants in `src/state.property.test.ts`, and to the model of App.tsx if it changes what is compared. The coverage counts there are `Record`s over the screen and action types, so `tsc -b` fails until each has an entry, and the weighted comparison then fails until a generator reaches the screen (a few hundred views) and each action changes the state (200 times unless given a lower floor). The invariants for the new screen are not checked by anything: those are yours to write.
6. Add its words to `src/copy.ts`.

### Limits

- The step-by-step comparison proves the reducer equals a model of the old App.tsx, written from its code, not the old App.tsx itself: a mistake in the model would hide a behavior change. The journeys drive the real build.
- The lint keeping `state.ts` pure is a tripwire, not a wall (see the known gaps in `scripts/boundaries.test.mjs`).
- `small` is compared only while planning: the reducer drops it once a block starts, the old App kept it through the block, Close and Closed, and every way back to planning reset it. A future way back to Pick would have to decide.
- Still open (BG-1), a product call and not changed here: a reload in the middle of Name loses its step and draft, and in Ask its item; Back from Pick or Ask lands on the first sub-step. Both are component state in `App.tsx` today. The union makes either fix small: add `phase` to `Name` and `idx` to `Ask`.

Differences from the old App.tsx that nobody can see:

- The reducer ignores actions the UI never offers: Two questions with no item, Start the block without a choice, a block action under an overlay.
- `choose` with an id that is not on the pick list clears the choice (`chosenId` becomes null) rather than being ignored; the UI only offers listed items.
- Pulling in another tab's save re-subscribes when the open day's date changes, not on every change of the day, and compares with the reducer's current day.
- Closing a day carried past midnight is two transitions, as above.
- A day stored closed with a running block (only a hand-edited store; no tab writes it) stays on Closed; the old App settled the block as soon as it opened such a day (on load, or from another tab's save), sent "Your block is done" if it had reached its target, and showed Close on the closed day.
- When a rollover opens a day on which another tab has a running block, the old App settled it with the time of the last tick; the reducer settles it on the next tick, within a second.

## The method's rules

`src/method.ts` is the one home for the method's numbers. `RULES` lists each rule with where it comes from: `talk` (the talk says it; `ref` is the transcript timestamp and `quote` a verbatim piece of that line), `reading` (the app's reading of a line in the talk) or `app` (the app's own addition). The named constants the app uses (`MAX_ITEMS`, `BLOCK_MIN`, `BLOCK_CHOICES`, `BREAK_LIMIT_MS` and the rest) are read from `RULES`, and lint flags a bare hour cutoff, block length, item count or minutes-as-milliseconds anywhere else in `src/`. `src/method.test.ts` has one test per rule that pins its numbers as literals next to the talk's line.

There are two late cutoffs on purpose until a product decision is made: `LATE_CUTOFFS.welcomeFraming` (11:00, the Welcome framing and the bad-day check) and `LATE_CUTOFFS.pickWarning` (12:00, the Pick screen's line). Code asks `isLate(t, cutoff)` from `clock.ts`. A compile-time check in `method.ts` fails `tsc -b` when they become one value (delete the `@ts-expect-error` line and merge them) and when that line is removed while they still differ.

## The words on screen

`src/copy.ts` is the one home of every word the app shows: the Welcome (first visit, returning morning, late start, missed days), Name, Ask, Pick (including "Nothing got a yes"), block, Close, Closed, Your days and About screens, the header, the save note, the error screen in `main.tsx`, both notifications, and the tag labels, day counts and reminder status that `logic.ts` builds. `App.tsx` and `main.tsx` render only through `t(id)`, the `fmt` templates (the lines with a value in them: the close item line, the counts, the Pick block line, the Name notes, the paused line, the reminder line, the step dots' label; `fmt` holds no sentence of its own: each one is an entry with a kind and a `{placeholder}` that `fill()` fills, and `src/copy.test.ts` fails on a literal of four or more words in `fmt`) and the constants `BRAND` and `TALK_URL`; `logic.ts` and `reminder.ts` read their words from it; the journeys in `e2e/drive.mjs` import it, so a wording change moves the app and its assertions together. A line used in two places is one entry (the hour-before-email line on the first welcome and on every morning welcome, `Back` on Name, Ask and Your days, `Yes` on Ask and Close). Some of those ids are named for one screen and show on others, so a wording change there moves every place: `close.yes` is also Ask's Yes, `pick.eyebrow` is also Ask's last button, `twoQuestions` is the last Name button and the Ask eyebrow, `yourOneThing` is the block eyebrow and the Your days stand-in for a done day with no text (rewording the eyebrow rewrites those rows), and `back`, `next`, `about`, `done`, `yourDays` and `no` each show on more than one screen. The ids, kinds and refs ship to the browser with the text (about 1.5 KB gzip); if the table keeps growing, a build-time map to text only would drop them. `SITE_URL` is the site the journeys and `scripts/verify-live.mjs` check, and `DOMAIN_DISPLAY` the domain on the link preview card (`scripts/og/card.mjs`); the meta tags in `index.html` stay literal, since the page cannot import the module, and `check-text` holds them to the same spelling. Left in code on purpose: dates through `Intl` (month and day names, a month with its year), the block-length labels (`hrs()`, such as `1½h`), and the symbols `×`, `›` and ` · ` between tags.

Each entry has a kind, like the rules in `method.ts`: `quote` (the talk word for word; `ref` is the m:ss timestamp of the transcript line where the quoted words start), `paraphrase` (the talk in the app's words, with the timestamp of the line it paraphrases) or `own` (the app's own words, which the type forbids to carry a ref). What checks it:

- `src/copy.test.ts`, everywhere: every quote and paraphrase has an m:ss ref, no own entry has one, no two ids hold the same text, and the `REQUIRED` lines (sentences only) are on their screens in every listed state, rendered with `renderToStaticMarkup`. `@ts-expect-error` lines in the test make `tsc -b` prove the type rules.
- `src/copy.test.ts`, only with the transcript: each quote is in the talk word for word, ignoring case, commas, apostrophes and spacing but not sentence ends (a quote that ends with a period must end where the talk's sentence ends, so a quote cut short fails), starting on its ref line (any of them when the talk says it more than once); each paraphrase ref is a real timestamp. **The transcript is not in the repo** (the talk is someone else's content), so these run only where `FERRISS_TRANSCRIPT` points at a transcript file, locally and not in CI, and show as skipped when none is set. A path that is set but cannot be read, or a file with no `[m:ss]` lines, is one failing test naming the path, never a skip. `scripts/transcript.mjs` is the one way both this test and `npm run check:quotes` find it.
- `eslint.config.js` (`COPY_FILES`, inside `boundaries()`): inline text of four or more words anywhere in the app files (`App.tsx`, `main.tsx`, `logic.ts`, `reminder.ts` and the other owner modules), in a screen or a module-level constant alike, is an error that says to move it to `copy.ts`. It does not see strings of one to three words, text in a file not on the list (a new file has to be added), or a sentence joined from short pieces; `scripts/boundaries.test.mjs` fails if a listed file is renamed or moved, or stops being linted.
- `scripts/check-text.mjs` (in `npm run lint` and `npm run check:fast`): no em or en dash in what a person reads, the domain shown as DoTheHardThing.app (lowercase only in a URL or a code span that is only the hostname), the brand as Do The Hard Thing.

### Open product questions

- **Q1, the late cutoff.** The Welcome screen treats opening at or after 11:00 as a late start; the Pick screen shows its late line from 12:00. Both are kept as they were. Choosing one hour means deleting the `@ts-expect-error` line in `src/method.ts` and merging `LATE_CUTOFFS` into one value.
- **A trace of the cited transcript lines.** Committing the few transcript lines the quotes cite (about 8) would let CI check the quotes too. It is the owner's call whether verbatim lines of the talk belong in a public MIT repository; until then the quote checks are local only. A committed trace would also need its own guard, since CI could not tell a hand-edited trace from the talk.
- **The hour line on a late first visit.** The first welcome shows "Ideally an hour before email or screens." at any hour, also after the 11:00 cutoff where a returning welcome drops it. It was added to the first welcome unconditionally in an earlier change; before that a late first visit had no hour line. The required-lines test keeps today's behavior (`firstWelcomeLate` in `REQUIRED`); whether it is intended is open.

## Journeys, maps and the social card

Two checks in `npm run check:fast` (and so in CI) keep generated or hand-kept records from drifting. Neither needs a browser.

- `scripts/check-maps.mjs` (`npm run check:maps`) parses `e2e/drive.mjs` without running it. Every journey carries meta, `journey({ id, feature, proves, strings }, fn)`: the feature map that lists it, the sub-features it proves and the copy ids it asserts. The check fails when a journey has no meta, is listed in no map, in two maps or twice in one (any code span containing `vdt journey <name>` counts as a listing, such as `e2e/vdt journey <name>`), a sub-feature id is listed in two maps, a map names a journey that is gone (in a `vdt journey` line, a "see" reference, matched by its link target, or any backticked kebab-case name), a `strings` id is not in `src/copy.ts` or not asserted, or a sub-feature is proved by no journey without saying "not verified by vdt". The feature files stay hand-written: they carry the steps, clock moves and stored values a table could not. What it does not catch: a journey added outside `J` and the objects merged into it (`J.x = ...`, an alias such as `const J2 = J`, and an `Object.assign(J, x)` whose `x` is not an object literal or a top-level const holding one are reported; other ways are not; it does not compare with `node e2e/drive.mjs --list`, which imports Playwright and would add about 340 ms), prose that describes a journey without naming it, and a weak assertion: the `strings` reach check follows every helper a journey calls, so a helper that asserts a string on one branch counts. `proves` and `strings` are claims checked for existence and reach, not proof that the journey really verifies the sub-feature: a journey can list a sub-feature it never drives and the check passes.
- `scripts/check-og.mjs` (`npm run check:og`) guards `public/og-image.png`, whose words are pixels. `scripts/og/og-image.inputs.json` (outside `public/`, so it is never served) records the hashes of `scripts/og/card.mjs` and the fonts it embeds, the text of the copy ids and constants the card shows, the Pick block lengths, and the png's hash. The check fails when an input changed but the png did not, and when the png is not the recorded one; `--write` records a rebuilt card and refuses a stale one; it also refuses when there is no record, and the first record needs an explicit `--init`, so a deleted record cannot certify whatever png is there. Every `pick.*` and `tag.*` id in `src/copy.ts` is in `CARD_COPY` or in `NOT_ON_CARD` (with a reason), so a new Pick line fails until someone decides whether the card shows it. A dependency update that changes a font file fails it too, and the card then has to be rebuilt locally, since CI has no browser. The inputs are only the declared ones: a CSS or layout change on Pick does not trigger it. `--pixels` re-renders the card and compares pixels, and also checks that every line the phone shows is a declared input; it is local only, because a different Chromium build differs by thousands of pixels with the same inputs.

## Local-first

There is no account and no server-side copy of anything a person writes. The whole state is one JSON value in `localStorage` under the key `one-thing:v3`: the list of days (items, the chosen one, the block, the "Did you do it?" answer), the reminder time, and a small per-month archive of finished-day counts for days that have aged out of the stored window (the 120 most recent days). The service worker precaches the app shell, so it loads and works offline.

A second key, `one-thing:events`, records only which anonymous count names were already sent today, so a refresh does not count twice.

### Why the keys are still called `one-thing:*`

The project began under the working name "One Thing". The keys are part of the stored data format, and people already have days saved under them. Renaming a key would make the app look empty on their next visit, so the keys keep their original prefix. The previous format, `one-thing:v2`, is read once to migrate into v3 and is never written or deleted. Any change to the stored shape should add a new versioned key and a migration, not rename an old one.

## Time

The app depends on the device's local clock: a day is the local calendar date, and a block belongs to the day it started. The end-to-end journeys use Playwright's fake clock to move time.

## Anonymous counts

The client sends at most three events (`started`, `finished`, `opened_history`), once per browser per day, as `POST /api/event` with `{"event":"<name>"}`. Nothing is sent in development or when the browser signals Do Not Track or Global Privacy Control. The Worker allow-lists the name and writes a data point to Workers Analytics Engine containing the event name and the country code from Cloudflare's request metadata. It does not store IP addresses or user agents. See the Analytics section of the [README](../README.md).

## Hosting

What the hosting config promises, and the check that holds it:

- **Theme color.** The light `<meta name="theme-color">` in `index.html` (`#f4f3ef`, the paper) owns the color of the installed app's title bar and splash. `vite.config.ts` repeats it as a literal in the manifest's `theme_color` and `background_color` (the config has no Node types to read `index.html` with), and `npm run check:dist` fails when either, or the light `--paper` in the built CSS, differs from the meta tag. The dark meta tag (`#15181d`) has no manifest counterpart: a manifest holds one color. The icons keep their charcoal (`#1f2329`, the ink color) background.
- **Security headers.** One `/*` rule in `public/_headers` gives every static response `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()` (features the app never uses; notifications and the service worker are not governed by it) and `X-Frame-Options: DENY` (no other site can frame the pages). The values live once, in `POLICY` in `scripts/headers-policy.mjs`, which also holds the `_headers` parser that `check:dist` and `verify:live` share. `npm run check:dist` fails when `/`, `/sw.js`, `/manifest.webmanifest`, a hashed `/assets/*.js` or an unknown path such as `/nope` (the single-page-app fallback; Cloudflare matches `_headers` on the request path) lacks one of them or gets another value. None of the four can block the optional Cloudflare Web Analytics beacon (the `static.cloudflareinsights.com` script and its request to `cloudflareinsights.com`): none restricts scripts or connections.
- **Not the Worker.** Cloudflare applies `_headers` only to static asset responses, not to responses the Worker makes, so `/api/event` gets none of these headers (it returns no page).
- **Left out on purpose.** No `Strict-Transport-Security`: the `.app` TLD is on the browsers' HSTS preload list, so browsers already refuse plain HTTP for the domain; which subdomains exist beyond `www` is not known to the repo, and `includeSubDomains` is hard to undo once browsers have cached it. No `Content-Security-Policy` yet. `verify:live` reports both as INFO (`LEFT_OUT` in `scripts/headers-policy.mjs`).
- **www.** `www.dothehardthing.app` is a custom domain of the Worker in `wrangler.jsonc` (its DNS record and certificate); a Cloudflare redirect rule, created by hand in the dashboard and not by the repo or CI, should send it to the bare domain with a 301. The runbook is [www-redirect.md](./www-redirect.md); `npm run verify:live -- --www` reports it (PENDING until the rule exists, `--require-www` to fail instead). CI cannot prove it.
- **Live checks of this build.** `npm run verify:live` compares the live `manifest.webmanifest` with `dist/`'s, and the headers live `/` gets with what `dist/_headers` gives `/` (`content-type` aside, per header name, whitespace collapsed; headers the edge adds are ignored). These checks of this build's files are a FAIL only with `--post-deploy` ("I just deployed this build"), which the deploy job passes and `check:workflows` requires; without it a mismatch prints `PENDING ...; run with --post-deploy after the deploy`, which never fails the run on its own, so the checks can run against the live site before a deploy. The entry script cannot decide it: a change to `_headers` or the manifest alone changes no JS, so the entry script is the same before and after the deploy. `scripts/verify-live.test.mjs` runs it against a local fake site.

## Deploy

`npm run build` writes `dist/`. `npx wrangler deploy` uploads `dist/` as static assets and deploys the Worker. See the README for what a fork must change.

CI deploys from `.github/workflows/ci.yml` (the README's Automatic deploy section has the steps):

- **The gate.** `deploy` needs both `check` and `journeys`, and runs only for a push to `master` in this repository. It once needed `check` alone, so a master build whose journeys failed could have gone live.
- **The preflight.** The `check` job runs `wrangler deploy --dry-run` with no credentials: it reads `wrangler.jsonc` and `dist/` and checks the assets and bindings. It cannot see the account: whether Analytics Engine is enabled on it, or whether the API token has the permissions the deploy needs. Those fail only in the real deploy (see "Before the first deploy" in the README). Both use the one workflow-level `WRANGLER_VERSION`.
- **The environment.** The deploy job declares the `production` environment (a deployment history; a required reviewer can be added in the repository settings). It runs one at a time, is never cancelled halfway, holds the Cloudflare secrets only in its deploy step's env, and after the deploy only reads the live site (`npm run verify:live -- --retries 10 --post-deploy`, so a manifest or header that differs from the build fails the job).
- **The guard.** `npm run check:workflows` (in `npm run check`) parses the workflows and `.github/dependabot.yml` and fails when one of these properties goes: the needs, the `if` (push to master only, no `||` or `always()`), where secrets appear and the one-line step that holds them, read-only permissions, sha-pinned actions, the fast journeys on pull requests only, the dry run, `verify:live` with `--post-deploy` and no POST, the pinned Wrangler, timeouts, concurrency and the environment, no `continue-on-error`, the triggers (push to master and pull requests, never `pull_request_target`), a real deploy only in the deploy job, and the Dependabot groups and major ignore. A shape it cannot read is reported with the file and the rule, never a stack trace. It checks names and shapes, not logic: an `if` that can never be true, a step that never runs, or a shell bug passes it. `actionlint`, run by hand when the workflows change, covers syntax and shell.
